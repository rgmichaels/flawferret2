# Framework Builder: Show Scenario Name in Smoke Test Result

Status: Draft
Date: 2026-08-17

Jira: FLW-8

## Problem

When the framework wizard runs the generated smoke test (`pnpm test:smoke`,
i.e. `cucumber-js --tags @smoke`), the result card in the UI only shows a
hardcoded generic message — `"Generated smoke test passed."` /
`"Generated smoke test failed."` — with no indication of which scenario
was actually exercised. The user has to expand the raw stdout `<pre>` block
to find the scenario name, if they can find it at all. The Jira screenshot
shows this generic "1 scenario passed" style output with no scenario title.

## Proposed change

`validateFrameworkSmokeTest()` in `apps/api/src/framework-validation.ts`
(~lines 216–269) builds its `message` field as a literal string. It has
access to raw `stdout`/`stderr` from the `pnpm test:smoke` run, but no
structured data.

Good news: every framework generated by the wizard already configures
Cucumber to emit a machine-readable JSON report on every run — see
`apps/api/src/framework-template.ts` (~line 494-506), the scaffolded
`cucumber.js`:

```js
export default {
  format: [
    "progress",
    "json:reports/cucumber-report.json",
    "html:reports/cucumber-report.html"
  ],
  ...
};
```

So `--tags @smoke` runs already write `reports/cucumber-report.json` in
the target directory — no framework template change needed, and no need to
scrape plain-text `stdout`. The fix is entirely in
`validateFrameworkSmokeTest()`:

1. After `runner("pnpm", ["test:smoke"], ...)` resolves (success path) or
   throws (failure path), read and parse
   `join(targetDirectory, "reports", "cucumber-report.json")`.
2. The `@cucumber/cucumber` JSON formatter output is an array of features,
   each with `elements` (scenarios), each with a `name`, `keyword`
   (`"Scenario"`), and `steps[].result.status`. Extract, per scenario:
   `name`, and a derived `status` (`"passed"` if every step's
   `result.status === "passed"`, else `"failed"`; treat `"skipped"`/
   `"undefined"`/`"pending"` step statuses as not-passed).
3. Add a new `scenarios` array to the result (see schema change below) and
   build a more specific `message`, e.g.:
   - One scenario: `"Configured base URL loads successfully" passed.`
   - Multiple scenarios, all passed: `All 3 scenarios passed: "A", "B", "C".`
   - Mixed/failed: `1 of 3 scenarios failed: "B".` (list only the failing
     names to keep the message short; full list still available via
     `scenarios`).
4. If the report file is missing, empty, or fails to parse (e.g. the run
   crashed before Cucumber wrote anything, or a user hand-edited
   `cucumber.js` and removed the JSON formatter), fall back to today's
   generic message and set `scenarios: []` — don't fail the whole
   validation over a missing/malformed report.
5. Reading `reports/cucumber-report.json` should not itself be allowed to
   throw and mask the real pass/fail result — wrap the read+parse in a
   try/catch and fall back per point 4.

### Schema change

`packages/job-schemas/src/index.ts`,
`frameworkSmokeValidationResponseSchema` (~line 631) gains an optional
field:

```ts
scenarios: z
  .array(
    z.object({
      name: z.string(),
      status: z.enum(["passed", "failed"]),
    }),
  )
  .optional(),
```

No DB migration needed: `FrameworkBuild.smokeValidationResult` is already
`Json?` (`packages/db/prisma/schema.prisma` ~line 182), so the extra field
persists automatically.

### UI change

`apps/web/app/framework/new/page.tsx` — `FrameworkActionResultCard` (~line
465) already renders `message` prominently as `<strong>{message}</strong>`,
so a richer `message` string (per point 3 above) is visible without any
markup change to that component. Optionally (nice-to-have, not required for
"done"): render the `scenarios` list explicitly, e.g. a small list under the
summary line showing each scenario name with a pass/fail marker, instead of
relying solely on the composed message string. The build detail page
(`apps/web/app/framework/builds/[id]/page.tsx`, ~line 164) reads
`build.smokeValidationResult` through the same `getActionResult`/result-card
path and will pick up the richer `message` automatically once the API
returns it, since it's stored verbatim as JSON.

### Files touched

- `apps/api/src/framework-validation.ts` — read/parse the JSON report,
  build `scenarios` + richer `message`.
- `apps/api/src/framework-validation.test.ts` — new test cases (see
  acceptance criteria).
- `packages/job-schemas/src/index.ts` — add `scenarios` to
  `frameworkSmokeValidationResponseSchema`.
- `apps/web/app/framework/new/page.tsx` — no required change (message
  already renders); optional scenario-list rendering.
- No changes needed to `apps/api/src/framework-template.ts` (JSON formatter
  already scaffolded) or `packages/db/prisma/schema.prisma` (already `Json?`).

## User stories / acceptance criteria

- As a user running the framework wizard's smoke validation, I can see the
  actual scenario name(s) that were exercised in the result summary, not
  just a generic pass/fail count.
- Given a smoke run with exactly one scenario that passes, when validation
  completes, then `message` includes that scenario's name and reads as
  passed (e.g. `"Configured base URL loads successfully" passed.`).
- Given a smoke run with multiple `@smoke`-tagged scenarios that all pass,
  when validation completes, then `message` names or counts all of them
  clearly (not just "N scenarios passed").
- Given a smoke run where one or more scenarios fail, when validation
  completes, then `message` identifies which scenario(s) failed by name.
- Given `reports/cucumber-report.json` is missing or unparsable after the
  run, when validation completes, then the existing generic
  passed/failed message is used as a fallback and `scenarios` is `[]` —
  the smoke run's actual pass/fail `status`/`exitCode` must still be
  correct and must not be affected by report-parsing failures.
- Given the API response now includes `scenarios`, when the framework
  wizard's validate step and the build detail page render the result, then
  no runtime/type error occurs (schema updated in `job-schemas`, consumed
  as optional).

## Out of scope

- Changing what `@smoke`-tagged scenarios exist in the generated framework
  template, or how many are scaffolded by default.
- Parsing/surfacing the fuller Cucumber JSON report (step-level detail,
  error messages/stack traces per step) — this spec covers scenario
  name + pass/fail only.
- Applying the same structured-output treatment to `pnpm test` /
  `test:api` / `test:a11y` or any other non-smoke validation command — this
  is scoped to `validateFrameworkSmokeTest()` specifically, since that's
  what FLW-8 and the screenshot are about.
- Any change to `installFrameworkDependencies` or `openFrameworkFolder`.
- A dedicated UI component redesign for the scenario list (the optional
  list-rendering noted above is a nice-to-have, not required).

## Open questions

None blocking — the JSON formatter is already scaffolded in every generated
framework, so this can proceed as a self-contained change to
`validateFrameworkSmokeTest()` plus the schema field. One minor judgment
call left to `coder`: exact wording/formatting of the composed `message`
string for the "multiple scenarios, mixed pass/fail" case — the acceptance
criteria above constrain it (must name the failing scenario(s)) but don't
mandate an exact string.
